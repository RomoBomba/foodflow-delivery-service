# FoodFlow

Учебный веб-сервис заказа готовой домашней еды от локальных кухонь. Клиент выбирает блюда с учётом пищевых предпочтений, оформляет заказ и отслеживает его статус. Кухня управляет меню и заказами, администратор проверяет кухни и модерирует отзывы.

Проект команды Университета ИТМО по дисциплине «Разработка решений на технологических платформах».

## Состояние проекта

Разрабатывается серверная часть MVP.

- [x] Spring Boot-приложение на Java 21.
- [x] PostgreSQL в Docker Compose с постоянным томом.
- [x] Flyway и миграции базы данных.
- [x] Регистрация с нормализацией email и хешированием пароля.
- [x] Вход через серверную сессию, выход и текущий пользователь.
- [x] CSRF-защита изменяющих запросов.
- [x] Заявки кухонь, одобрение, отклонение и блокировка.
- [x] Справочники категорий и ингредиентов.
- [x] Создание блюд и просмотр меню своей кухни.
- [x] Публичный каталог и карточка блюда.
- [x] Фильтры, сортировка по цене и пагинация каталога.
- [ ] Редактирование, архивирование и переключение приёма заказов — завершающая проверка.
- [ ] Корзина, оформление заказов и резервирование порций.
- [ ] Предпочтения и персональный подбор.
- [ ] Отзывы, рейтинг и модерация отзывов.

Чек-лист обновляется по результатам проверки функций. Архитектурные диаграммы описывают целевую систему и могут включать ещё не реализованные компоненты.

## Возможности MVP

| Участник | Целевые возможности |
| --- | --- |
| Гость | Каталог, карточки блюд, регистрация и вход |
| Клиент | Предпочтения, персональный подбор, корзина, оформление и история заказов, отмена до приготовления, отзывы |
| Представитель кухни | Собственное меню, цены и остатки, приём и обработка заказов своей кухни |
| Администратор | Одобрение, отклонение и блокировка кухонь, скрытие отзывов с указанием причины |

Заявку кухни подаёт зарегистрированный клиент. После одобрения он получает роль `KITCHEN`.

Основные правила целевой версии:

- Один заказ содержит блюда одной кухни.
- Корзина включает до 30 разных блюд, по 1–99 порций каждого.
- При оформлении сервер повторно проверяет цены, доступность и остатки.
- Заказ, снимки позиций и резерв сохраняются одной транзакцией.
- Повтор оформления с тем же ключом не создаёт второй заказ.
- Отмена возвращает зарезервированные порции ровно один раз.
- Статусы заказа: **Создан → Готовится → В доставке → Выполнен**. Из состояния «Создан» также возможна отмена.
- Отзыв разрешён только по своему выполненному заказу.

Персональный подбор будет учитывать любимую категорию, ингредиенты и калорийность с весами **50/30/20**, нормированными по заданным критериям. Исключённые ингредиенты проверяются отдельно. Оценки покупателей не входят в персональный балл.

В MVP предусмотрены оплата при получении, адрес текстом и ручная смена статусов кухней. Обновление кабинетов заказов планируется раз в 15 секунд.

Банковская оплата, курьерские API, GPS, SMS, email и автоматическое составление рациона находятся за границами MVP.

## Стек и архитектура

| Часть | Технологии |
| --- | --- |
| Backend | Java 21, Spring Boot 4.1.2, Maven, Spring Data JPA |
| Доступ | Spring Security, серверные сессии, cookie, CSRF |
| Пароли | PBKDF2 через Spring Security |
| База данных | PostgreSQL 17, Flyway |
| Frontend — запланирован | React, TypeScript, Vite |
| Запуск | Docker Compose; Nginx для будущей сборки frontend |
| Тестирование | JUnit; интеграционные и приёмочные проверки развиваются вместе с функциями |

Backend строится как **модульный монолит** — одно приложение с пятью предметными модулями.

| Модуль | Ответственность |
| --- | --- |
| `identity` | Аккаунты, вход и права доступа |
| `catalog` | Кухни, блюда, справочники и свободные остатки |
| `recommendation` | Предпочтения и объяснимый подбор |
| `ordering` | Корзины, заказы, резервы и история статусов |
| `feedback` | Отзывы, рейтинг и модерация |

Сейчас реализуются `identity` и `catalog`. Остальные модули запланированы.

Внутри модулей используются контроллеры, сервисы, репозитории и отдельные объекты ответа API. Межмодульные обращения проходят через сервисные контракты. Доступ к данным проверяется на сервере.

## Локальный запуск

Нужны **JDK 21**, **Git** и запущенный **Docker с Compose**. Maven Wrapper входит в проект — отдельная установка Maven не требуется.

Сейчас PostgreSQL запускается в контейнере, backend — локально из IntelliJ IDEA или терминала. Frontend и запуск всего приложения одной командой будут добавлены отдельно.

### 1. Настроить окружение

Из корня клонированного репозитория:

```bash
cp .env.example .env
```

В `.env` задать локальный пароль PostgreSQL:

```dotenv
POSTGRES_PASSWORD=your_local_password
```

`.env` не коммитится. В репозитории хранится `.env.example` без настоящих секретов.

### 2. Запустить PostgreSQL

```bash
docker compose up -d postgres
docker compose ps
```

Дождаться состояния `healthy`.

| Параметр | Значение |
| --- | --- |
| Адрес с локального компьютера | `localhost:5433` |
| База данных | `foodflow` |
| Пользователь | `foodflow` |

### 3. Запустить backend

В IntelliJ IDEA:

1. Импортировать `backend/pom.xml` как Maven-проект.
2. Выбрать JDK 21.
3. В конфигурации запуска `BackendApplication` добавить переменную окружения:

```text
DB_PASSWORD=your_local_password
```

Значение должно совпадать с `POSTGRES_PASSWORD` из `.env`.

**Compose читает `.env` автоматически, Java-приложение из IDE — нет.**

Запустить `BackendApplication`. Flyway автоматически применит новые миграции из:

```text
backend/src/main/resources/db/migration
```

Для запуска из терминала сначала настроить переменную окружения `DB_PASSWORD`, затем выполнить из корня:

```bash
./backend/mvnw -f backend/pom.xml spring-boot:run
```

### 4. Проверить запуск

```bash
curl http://localhost:8080/api/health
```

Ожидаемый ответ:

```json
{"status":"UP","application":"FoodFlow"}
```

Проверить каталог:

```bash
curl 'http://localhost:8080/api/dishes?page=0&size=20'
```

На чистой базе каталог будет пустым, пока кухня не подаст заявку, не получит одобрение и не создаст блюда.

История миграций:

```bash
docker compose exec postgres psql -U foodflow -d foodflow \
  -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
```

Остановить базу без удаления данных:

```bash
docker compose stop postgres
```

### Локальный администратор

Для создания администратора добавить в конфигурацию запуска backend:

```text
SPRING_PROFILES_ACTIVE=local
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=your_local_admin_password
```

Пароль должен содержать 12–128 символов. Создание аккаунта выполняется при запуске приложения с профилем `local`.

- Публичная регистрация создаёт только `CLIENT`.
- Существующий администратор не создаётся повторно.
- Изменение `ADMIN_PASSWORD` не сбрасывает пароль существующего аккаунта.
- Если email занят пользователем без роли `ADMIN`, автоматическое повышение прав не выполняется.
- Учётные данные задаются локально и не сохраняются в Git.

### Переменные окружения

| Переменная | Назначение | Значение |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL для Compose | Задаётся в `.env` |
| `DB_PASSWORD` | Пароль подключения backend | Совпадает с `POSTGRES_PASSWORD` |
| `DB_URL` | Адрес БД для backend | По умолчанию `jdbc:postgresql://localhost:5433/foodflow` |
| `DB_USERNAME` | Пользователь БД | По умолчанию `foodflow` |
| `SPRING_PROFILES_ACTIVE` | Активный профиль | `local` для локального создания администратора |
| `ADMIN_EMAIL` | Email локального администратора | Задаётся разработчиком |
| `ADMIN_PASSWORD` | Пароль локального администратора | Задаётся разработчиком |
| `SESSION_COOKIE_SECURE` | Флаг Secure у cookie | `false` локально; `true` на HTTPS-стенде |

Данные PostgreSQL сохраняются в томе `postgres_data`. Удаление тома удаляет локальную БД. Изменение пароля только в `.env` после инициализации не меняет пароль существующего пользователя БД.

## API

Базовый адрес локального backend: `http://localhost:8080`.

### Аккаунты и справочники

| Метод | Адрес | Назначение | Доступ |
| --- | --- | --- | --- |
| GET | `/api/health` | Проверка приложения | Публичный |
| GET | `/api/categories` | Категории блюд | Публичный |
| GET | `/api/ingredients` | Ингредиенты | Публичный |
| GET | `/api/auth/csrf` | CSRF-токен | Публичный |
| POST | `/api/auth/register` | Регистрация | Публичный, с CSRF |
| POST | `/api/auth/login` | Вход | Публичный, с CSRF |
| GET | `/api/auth/me` | Текущий пользователь | После входа |
| POST | `/api/auth/logout` | Выход | С CSRF |

Регистрация принимает JSON с `email` и `password`. Вход принимает `application/x-www-form-urlencoded` с теми же полями.

### Кухни и модерация

| Метод | Адрес | Назначение | Доступ |
| --- | --- | --- | --- |
| POST | `/api/kitchens` | Подать заявку | `CLIENT` |
| GET | `/api/kitchens/me` | Своя заявка или кухня | `CLIENT`, `KITCHEN` |
| GET | `/api/admin/kitchens?status=PENDING` | Список по статусу | `ADMIN` |
| POST | `/api/admin/kitchens/{id}/approve` | Одобрить заявку | `ADMIN` |
| POST | `/api/admin/kitchens/{id}/reject` | Отклонить с причиной | `ADMIN` |
| POST | `/api/admin/kitchens/{id}/block` | Заблокировать с причиной | `ADMIN` |

Статусы кухни: `PENDING`, `APPROVED`, `REJECTED`, `BLOCKED`.

Одобрение разрешено только для `PENDING` и атомарно выдаёт владельцу роль `KITCHEN`. Для обновления прав в существующей сессии владельцу нужно заново войти.

Отклонение разрешено для `PENDING`, блокировка — для `APPROVED`. Оба запроса принимают JSON:

```json
{
  "reason": "Причина решения"
}
```

Блокировка выключает приём заказов, но сохраняет роль владельца. При реализации заказов она также должна запрещать новые покупки, сохраняя обработку уже созданных.

### Блюда

| Метод | Адрес | Назначение | Доступ |
| --- | --- | --- | --- |
| GET | `/api/dishes` | Публичный каталог | Публичный |
| GET | `/api/dishes/{id}` | Карточка блюда | Публичный |
| GET | `/api/kitchens/me/dishes` | Меню своей кухни | `KITCHEN` |
| POST | `/api/kitchens/me/dishes` | Создать блюдо | `KITCHEN`, кухня одобрена |

Завершаемые endpoints управления меню:

| Метод | Адрес | Назначение | Доступ |
| --- | --- | --- | --- |
| PUT | `/api/kitchens/me/dishes/{id}` | Полностью обновить блюдо | `KITCHEN`, своя одобренная кухня |
| DELETE | `/api/kitchens/me/dishes/{id}` | Архивировать блюдо | `KITCHEN`, своя одобренная кухня |
| PATCH | `/api/kitchens/me/availability` | Включить или выключить приём заказов | `KITCHEN`, кухня одобрена |

Архивирование сохраняет запись, но скрывает блюдо из публичного каталога. Архивное блюдо нельзя редактировать.

Переключение приёма заказов принимает JSON:

```json
{
  "acceptingOrders": true
}
```

Каталог показывает неархивные блюда одобренных кухонь. Поле `available` дополнительно учитывает приём заказов кухней и положительный свободный остаток.

### Фильтры каталога

Пример:

```text
GET /api/dishes?minPrice=200&maxPrice=500&availableOnly=true&page=0&size=20&sort=priceAsc
```

| Параметр | Назначение |
| --- | --- |
| `kitchenId` | Фильтр по UUID кухни |
| `categoryId` | Фильтр по UUID категории |
| `minPrice`, `maxPrice` | Диапазон цены включительно |
| `availableOnly` | Только доступные для заказа блюда; по умолчанию `false` |
| `page` | Номер страницы с нуля |
| `size` | Размер страницы: 1–100, по умолчанию 20 |
| `sort` | `priceAsc` или `priceDesc`, по умолчанию `priceAsc` |

Ответ каталога содержит `content`, `page`, `size`, `totalElements` и `totalPages`. Выход за пределы страниц возвращает пустой `content`.

Сортировка по персональному баллу будет добавлена вместе с рекомендациями.

## Сессии и CSRF

Авторизация использует cookie `JSESSIONID`. Таймаут бездействия сессии — 30 минут.

Для изменяющих запросов:

1. Вызвать `GET /api/auth/csrf`, сохранив cookie.
2. Передать полученный токен в заголовке, указанном полем `headerName`, вместе с cookie.
3. После входа и выхода получить новый CSRF-токен.

`permitAll` не отключает CSRF-защиту. Вызов POST без токена может вернуть `403` до проверки пароля.

После перезапуска backend требуется новый вход: сессии хранятся в памяти процесса. Данные пользователей, кухонь и блюд сохраняются в PostgreSQL.

Cookie-файлы для ручных проверок хранятся в `.local/`. Эта папка не коммитится.

### Основные HTTP-ответы

| Код | Значение |
| --- | --- |
| `200` | Успешное чтение или изменение |
| `201` | Создан пользователь, кухня или блюдо |
| `204` | Успешный вход, выход или архивирование |
| `400` | Некорректные поля или параметры |
| `401` | Требуется вход или неверные учётные данные |
| `403` | Недостаточно прав или не прошла CSRF-проверка |
| `404` | Объект не найден либо недоступен в данном контексте |
| `409` | Конфликт данных или недопустимое состояние |

## Дальнейшая разработка

1. Завершить проверку управления меню и объединить ветку каталога.
2. Реализовать сохраняемую корзину одной кухни.
3. Добавить оформление заказа, снимки цен и резервирование порций.
4. Реализовать статусы, историю и отмену заказа.
5. Проверить повторные запросы и конкурентный доступ к остаткам.
6. Добавить предпочтения, персональный подбор, отзывы и рейтинг.
7. Параллельно подключить frontend к готовым API.
8. Подготовить общий запуск, демонстрационные данные, резервное копирование и приёмочные проверки.

Готовность MVP определяется выполнением **FR-01–FR-21 и NFR-01–NFR-10** из ТЗ. Показатели производительности и надёжности являются целями испытаний, а не уже достигнутыми результатами.

## Работа с кодом

- `main` содержит рабочую общую версию.
- Каждая задача выполняется в отдельной ветке и объединяется через pull request.
- Перед объединением проверяются изменения, сборка, запуск и сценарии задачи.
- README обновляется вместе с функциями и настройками запуска.
- Структура БД меняется только миграциями Flyway.
- Уже применённые миграции не редактируются; номера новых миграций согласуются между участниками.
- `.env`, `.local/`, настройки IDE, пароли и результаты сборки не сохраняются в Git.
- Maven Wrapper сохраняется в репозитории.

Тесты backend запускаются при доступной локальной БД и настроенной в терминале переменной `DB_PASSWORD`:

```bash
./backend/mvnw -f backend/pom.xml test
```

Изоляцию интеграционных тестов от рабочей локальной БД предстоит добавить. Ручные проверки через `curl` не заменяют автоматические тесты.

Ключевые сценарии приёмки: доступ к чужим данным, повтор оформления, последняя порция, гонка принятия и отмены, сохранность цены и восстановление из копии.
