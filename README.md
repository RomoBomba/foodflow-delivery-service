# FoodFlow

Учебный веб-сервис заказа готовой домашней еды от локальных кухонь. Клиент выбирает блюда с учётом пищевых предпочтений, оформляет заказ и отслеживает его статус. Кухня управляет своим меню и заказами, администратор проверяет кухни и модерирует отзывы.

Проект команды Университета ИТМО по дисциплине «Разработка решений на технологических платформах».

## Состояние проекта

Идёт разработка MVP. Подготовлена серверная основа:

- [x] Spring Boot-приложение на Java 21.
- [x] Проверочный endpoint `GET /api/health`.
- [x] PostgreSQL в Docker Compose с постоянным томом.
- [x] Flyway и миграции базы данных.
- [x] Справочник категорий: `GET /api/categories`.
- [x] Регистрация с нормализацией email и хешированием пароля.
- [x] Вход через серверную сессию, выход и текущий пользователь.
- [x] CSRF-защита изменяющих запросов.
- [ ] Заявки кухонь, модерация и управление меню.
- [ ] Корзина, заказы и резервирование порций.
- [ ] Предпочтения, рекомендации и отзывы.
- [ ] Frontend и общий запуск приложения.

Полный пользовательский сценарий пока не реализован. Список ниже описывает целевой объём.

## Возможности MVP

| Участник | Возможности |
| --- | --- |
| Гость | Просмотр каталога и карточек блюд, регистрация и вход |
| Клиент | Пищевые предпочтения, персональный подбор, корзина, оформление и история заказов, отмена до приготовления, отзывы |
| Представитель кухни | Заявка на подключение, собственное меню, цены и остатки, обработка заказов своей кухни |
| Администратор | Одобрение, отклонение и блокировка кухонь, скрытие отзывов с указанием причины |

Основные правила:

- Один заказ содержит блюда одной кухни. Корзина — до 30 разных блюд, по 1–99 порций каждого.
- При оформлении сервер проверяет цены и остатки. Заказ, снимки позиций и резерв сохраняются одной транзакцией.
- Повтор одного запроса не создаёт второй заказ. Отмена возвращает порции ровно один раз.
- Основные статусы: **Создан → Готовится → В доставке → Выполнен**. Из состояния «Создан» также возможна отмена.
- Отзыв доступен только по своему выполненному заказу.
- Персональный балл учитывает категорию, любимые ингредиенты и калорийность с весами **50/30/20**, нормированными по заданным критериям. Исключённые ингредиенты проверяются отдельно. Оценки покупателей не входят в персональный балл.

В первой версии предусмотрены оплата при получении, адрес текстом и ручная смена статусов кухней. Кабинеты заказов опрашивают сервер раз в 15 секунд. Банковская оплата, курьерские API, GPS, SMS, email и автоматическое составление рациона находятся за границами MVP.

## API

Backend локально доступен по адресу `http://localhost:8080`.

| Метод | Адрес | Назначение |
| --- | --- | --- |
| GET | `/api/health` | Проверка работы приложения |
| GET | `/api/categories` | Категории блюд |
| GET | `/api/auth/csrf` | Получение CSRF-токена |
| POST | `/api/auth/register` | Регистрация клиента |
| POST | `/api/auth/login` | Вход |
| GET | `/api/auth/me` | Текущий пользователь |
| POST | `/api/auth/logout` | Выход |

Регистрация принимает JSON с `email` и `password`.
Вход принимает `application/x-www-form-urlencoded`
с полями `email` и `password`.

Авторизация использует cookie `JSESSIONID`.
Для изменяющих запросов требуется CSRF-токен:
сначала вызвать `/api/auth/csrf`, затем передать полученный
токен в указанном ответом заголовке вместе с cookie.

После входа и выхода CSRF-токен необходимо получить заново.
`permitAll` не отключает CSRF-защиту.

Основные ответы: `201` — регистрация, `204` — вход и выход,
`400` — ошибка полей, `401` — требуется вход или неверный пароль,
`403` — нет доступа либо не прошла CSRF-проверка,
`409` — конфликт данных.

## Стек и архитектура

| Часть | Технологии |
| --- | --- |
| Backend | Java 21, Spring Boot 4.1.2, Maven, Spring Data JPA |
| База данных | PostgreSQL 17, Flyway |
| Доступ | Spring Security, серверная сессия, cookie и CSRF |
| Frontend — запланирован | React, TypeScript, Vite |
| Запуск | Docker Compose; Nginx для будущей сборки frontend |
| Тестирование | JUnit, интеграционные проверки с PostgreSQL |

Backend проектируется как **модульный монолит** — одно приложение с пятью предметными модулями:

| Модуль | Ответственность |
| --- | --- |
| `identity` | Аккаунты, вход и права доступа |
| `catalog` | Кухни, блюда, справочники и свободные остатки |
| `recommendation` | Предпочтения, фильтрация и объяснимый подбор |
| `ordering` | Корзины, заказы, резервы и история статусов |
| `feedback` | Отзывы, рейтинг и модерация |

Внутри модулей используются контроллеры, сервисы и репозитории. Межмодульные обращения проходят через сервисные контракты. Сервер проверяет роль и владельца объекта независимо от интерфейса.

## Локальный запуск

Нужны **JDK 21**, **Git** и запущенный **Docker с Compose**. Maven Wrapper входит в проект; отдельная установка Maven не требуется. Для будущего frontend потребуется Node.js; его версию зафиксируем при создании клиентского приложения.

Сейчас PostgreSQL запускается в контейнере, backend — локально из IntelliJ IDEA или терминала. Запуск всего приложения одной командой Compose запланирован отдельно.

### 1. Настроить окружение

Из корня клонированного репозитория:

```bash
cp .env.example .env
```

В `.env` задать локальный пароль:

```dotenv
POSTGRES_PASSWORD=your_local_password
```

Файл `.env` не коммитится. В репозитории хранится только `.env.example` без настоящих секретов.

### 2. Запустить PostgreSQL

```bash
docker compose up -d postgres
docker compose ps
```

Дождаться состояния `healthy`. База доступна с компьютера по адресу `localhost:5433`, имя базы и пользователь — `foodflow`.

### 3. Запустить backend

В IntelliJ IDEA импортировать `backend/pom.xml` как Maven-проект и выбрать JDK 21. В конфигурации запуска `BackendApplication` добавить переменную окружения:

```text
DB_PASSWORD=your_local_password
```

Значение должно совпадать с `POSTGRES_PASSWORD` в `.env`. Compose читает `.env` автоматически, но Java-приложение, запущенное из IDE, — нет.

Запустить `BackendApplication`. Flyway применит новые миграции из `backend/src/main/resources/db/migration`.

Альтернатива из терминала — сначала настроить переменную окружения `DB_PASSWORD`, затем выполнить из корня:

```bash
./backend/mvnw -f backend/pom.xml spring-boot:run
```

### 4. Проверить запуск

```bash
curl http://localhost:8080/api/health
```

Ожидаемый ответ, порядок полей может отличаться:

```json
{"status":"UP","application":"FoodFlow"}
```

Этот endpoint проверяет работу приложения. Историю миграций можно проверить отдельно:

```bash
docker compose exec postgres psql -U foodflow -d foodflow \
  -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
```

Остановить базу без удаления данных:

```bash
docker compose stop postgres
```

### Переменные окружения

| Переменная | Где используется | Значение |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | Compose, файл `.env` | Локальный пароль PostgreSQL |
| `DB_PASSWORD` | Backend | Тот же пароль PostgreSQL |
| `DB_URL` | Backend | По умолчанию `jdbc:postgresql://localhost:5433/foodflow` |
| `DB_USERNAME` | Backend | По умолчанию `foodflow` |

Данные сохраняются в томе `postgres_data`. Его удаление удалит локальную БД. После первой инициализации изменение пароля только в `.env` не меняет пароль существующего пользователя PostgreSQL.

## План разработки

1. Завершить справочник категорий и `GET /api/categories`.
2. Реализовать регистрацию, вход, выход и разграничение доступа.
3. Добавить кухни, модерацию, меню и каталог; параллельно подключить frontend.
4. Собрать сквозной заказ: корзина, оформление, резерв, кабинет кухни и статусы.
5. Проверить повторные запросы, последнюю порцию и конкурентную отмену.
6. Добавить предпочтения, персональный подбор, отзывы и рейтинг.
7. Подготовить общий запуск, демонстрационные данные, резервное копирование и приёмочные проверки.

Готовность MVP определяется выполнением **FR-01–FR-21 и NFR-01–NFR-10** из ТЗ. Показатели производительности и надёжности являются целями испытаний, а не уже достигнутыми результатами.

## Работа с кодом

- `main` содержит рабочую общую версию. Изменения вносятся через отдельные ветки и pull request.
- Одна ветка — одна законченная задача: например, `feature/categories-api` или `feature/auth`.
- Перед объединением проверяются сборка, запуск и результат задачи. Инструкция обновляется вместе с изменениями запуска.
- Схема БД изменяется только миграциями Flyway. Уже применённые миграции не редактируются; номера новых миграций согласуются между участниками.
- Пароли, `.env`, настройки IDE и результаты сборки не сохраняются в Git. Maven Wrapper сохраняется.

Тесты backend запускаются из корня при доступной локальной БД и настроенной в терминале переменной `DB_PASSWORD`:

```bash
./backend/mvnw -f backend/pom.xml test
```

Изоляцию интеграционных тестов от рабочей локальной БД предстоит добавить. Ключевые сценарии приёмки: доступ к чужим данным, повтор оформления, покупка последней порции, гонка принятия и отмены, сохранность цены и восстановление из копии.
