# FoodFlow

Учебный сервис заказа домашней еды от локальных кухонь. Проект команды Университета ИТМО.

Backend реализует каталог → корзину → оформление → обработку кухней → выполнение → отзыв. Также реализованы регистрация и сессии, модерация кухонь, предпочтения, объяснимые рекомендации и модерация отзывов. Frontend разрабатывается отдельно; React-приложение подключается к готовой конфигурации Nginx после сборки frontend.

Требования — в [ТЗ этапа 2](docs/FoodFlow_TZ_Stage2.docx), согласованная архитектура — в [диаграммах](docs/diagrams/). Контракты для frontend — в [API.md](docs/API.md).

## Стек и архитектура

Java 21, Spring Boot 4.1.2, Maven Wrapper, Spring MVC, Spring Security, JPA/Hibernate, PostgreSQL 17, Flyway. Пароли хешируются PBKDF2. Авторизация использует серверную HTTP-сессию, cookie `JSESSIONID` и CSRF.

Модульный монолит в пакете `com.foodflow`:

| Модуль | Назначение |
| --- | --- |
| `identity` | Пользователи, регистрация, вход, роли |
| `catalog` | Заявки кухонь, модерация, блюда, справочники |
| `recommendation` | Предпочтения, исключения, объяснимый подбор |
| `ordering` | Сохраняемая корзина, заказы, резерв, история статусов |
| `feedback` | Отзывы, агрегаты, модерация |
| `common` | Ошибки API, идентификаторы запросов |

Контроллеры принимают и возвращают DTO; бизнес-правила и транзакции находятся в сервисах. Схема меняется только Flyway, Hibernate работает с `ddl-auto=validate`. Между модулями вызываются сервисы; прямого доступа к репозиториям другого модуля нет. Применённые миграции не редактируются; изменение схемы добавляется новой миграцией.

Каждая позиция заказа имеет отдельный `Reservation`: `ACTIVE` при оформлении, `RELEASED` при отмене, `CONSUMED` при выполнении. Свободный остаток уменьшается при создании резерва и возвращается только при отмене. Версия заказа защищает действия по устаревшему состоянию.

## Локальный запуск для backend и frontend

Нужны Docker и Docker Compose. Из корня репозитория:

```bash
cp .env.example .env
```

В `.env` задайте собственный `POSTGRES_PASSWORD`. Для создания локального администратора добавьте:

```dotenv
SPRING_PROFILES_ACTIVE=local
ADMIN_EMAIL=admin@example.test
ADMIN_PASSWORD=replace_with_12_to_128_characters
```

Затем:

```bash
docker compose -f compose.yaml -f compose.dev.yaml up --build -d
docker compose -f compose.yaml -f compose.dev.yaml ps
curl --fail http://localhost:8080/api/health
```

Backend доступен на `http://localhost:8080`; PostgreSQL — `localhost:5433`. Локальная конфигурация публикует эти порты только на loopback и отключает Nginx. Сертификат и сборка frontend здесь не нужны. Разработчик frontend настраивает прокси Vite `/api` → `http://localhost:8080`; подробности сессии, CSRF и DTO — в [API.md](docs/API.md).

Backend внутри Compose подключается к `postgres:5432`. Первой сборке нужен интернет для образов и Maven-зависимостей. Backend запускается после готовности БД; применение миграций занимает дополнительное время. Ожидаемый ответ health: `{"status":"UP","application":"FoodFlow"}`. На чистой БД каталог пуст, справочники заполнены миграциями. Health проверяет HTTP-приложение, а не доступность БД отдельным запросом.

Диагностика и остановка:

```bash
docker compose -f compose.yaml -f compose.dev.yaml logs --tail=100 backend
docker compose -f compose.yaml -f compose.dev.yaml stop
```

Данные сохраняются в томе `postgres_data`. **Не используйте `down -v` для исправления миграций:** это удаляет БД. Изменение пароля в `.env` не меняет пароль уже инициализированного PostgreSQL.

### Запуск backend из IDE или терминала

Нужны JDK 21 и Docker:

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d postgres
cd backend
# Сначала задайте DB_PASSWORD в окружении терминала или IDE.
./mvnw spring-boot:run
```

В IDE импортируйте `backend/pom.xml`, выберите JDK 21, настройте окружение и запустите `BackendApplication`.

**Java-приложение не читает корневой `.env` автоматически.** `DB_PASSWORD` должен совпадать с `POSTGRES_PASSWORD`. Если порт 8080 занят контейнерным backend, сначала выполните `docker compose -f compose.yaml -f compose.dev.yaml stop backend` из корня.

| Переменная | Значение / назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Обязательный пароль БД для Compose |
| `DB_URL` | Локально по умолчанию `jdbc:postgresql://localhost:5433/foodflow` |
| `DB_USERNAME` | По умолчанию `foodflow` |
| `DB_PASSWORD` | Обязательный пароль БД для Java; Compose передаёт его автоматически |
| `SPRING_PROFILES_ACTIVE` | `local` включает создание администратора |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Учётные данные администратора; пароль 12–128 символов |
| `SESSION_COOKIE_SECURE` | Для Java: `false` для локального HTTP, `true` для HTTPS; Compose задаёт согласно выбранному режиму |

Администратор создаётся только при профиле `local`. Существующий пароль не сбрасывается; занятый обычным пользователем email не повышается до ADMIN. Публичная регистрация всегда создаёт CLIENT.

### Развёртывание через HTTPS по согласованной диаграмме

Основной `compose.yaml` запускает Nginx, backend и PostgreSQL. Наружу опубликован **только 443 Nginx**. Nginx завершает TLS, отдаёт статическую сборку React и проксирует `/api/` в backend. Cookie сессии имеет Secure. Backend и БД доступны только в сети Compose.

Перед запуском подготовьте:

- Сборку frontend с `index.html`, например `frontend/dist` после `npm run build` в проекте frontend.
- Сертификат домена `fullchain.pem` и ключ `privkey.pem` в `.local/tls` либо другом закрытом каталоге.
- При нестандартных путях — `FRONTEND_DIST` и `TLS_CERT_DIR` в `.env`. Относительные пути считаются от корня проекта.

```bash
docker compose up --build -d
docker compose ps
curl --fail https://your-domain.example/api/health
```

Для стенда нужен сертификат, доверенный браузером. Сертификат не выпускается автоматически. Отсутствующие каталоги сборки или TLS считаются ошибкой запуска. После замены сертификата выполните `docker compose exec nginx nginx -s reload`. Для локальных проверок порт и адрес привязки Nginx задаются через `HTTPS_PORT` и `HTTPS_BIND` (по умолчанию 443 и `0.0.0.0`). Не подключайте `compose.dev.yaml` на публичном стенде.

### Обновление существующей БД

Перед обновлением остановите старый backend и сохраните резервную копию. Новый backend применит V12 автоматически: `IN_DELIVERY` станет `DELIVERING`, появятся версия заказа, резервы каждой позиции и статусы отзывов. Остатки, история, снимки, отзывы и сведения о модерации сохраняются; повторного списания порций нет. V1–V11 не редактировались.

Старый backend несовместим со схемой после V12: его нельзя запускать одновременно с новым или просто вернуть поверх обновлённой БД. Возврат старой версии требует восстановления предварительной копии при остановленном приложении. Frontend нужно обновить на контракт `DELIVERING`, `version`/`expectedVersion` и `200` для повторного оформления; [точные запросы](docs/API.md).

### Демонстрационные данные и сквозная проверка

Нужен Python 3.9+ без сторонних пакетов. Backend должен быть запущен, администратор — создан. Задайте `ADMIN_EMAIL`, `ADMIN_PASSWORD` и выбранный `DEMO_PASSWORD` (8–128 символов) **в окружении терминала**:

```bash
python3 scripts/demo.py
python3 scripts/demo.py --smoke
```

Скрипт создаёт клиента `client@demo.test`, кухни `kitchen1@demo.test` … `kitchen3@demo.test` и 20 блюд через HTTP API. Пароль всех демоаккаунтов — `DEMO_PASSWORD`. Повторный запуск использует существующие аккаунты и блюда, не сбрасывает их пароли, цены и остатки; для входа нужен прежний пароль. При отклонённой или заблокированной демокухне скрипт останавливается.

`--smoke` очищает корзину и предпочтения **демоклиента**, оформляет одну порцию, повторяет запрос с тем же ключом, проводит заказ до COMPLETED и публикует отзыв. Каждый запуск создаёт новый заказ. Используйте скрипт только в учебной БД. Альтернативный адрес задаётся переменной `FOODFLOW_BASE_URL`. Для HTTPS с собственным доверенным центром сертификации укажите его PEM-файл в `FOODFLOW_CA_FILE`; проверка сертификата остаётся включённой.

## Бизнес-правила

- Корзина хранится в БД и содержит до 30 блюд одной кухни, по 1–99 порций. Смена кухни требует `confirmReplaceKitchen=true`. Добавление не резервирует остаток.
- Покупка разрешена только у APPROVED-кухни с включённым приёмом заказов, для неархивного блюда с достаточным остатком и без исключённых ингредиентов клиента.
- Оформление повторно проверяет корзину, цены, состав, остатки и кухню. Сумма вычисляется сервером через `BigDecimal`; стоимость доставки включена, валюта — рубли, оплата — при получении.
- При изменении цены возвращается `409 PRICE_CHANGED` с конкретным расчётом и отпечатком. Подтверждение старого расчёта после новой смены цены отклоняется.
- Заказ, снимки позиций, уменьшение остатка, история и очистка корзины сохраняются одной транзакцией. Блокировки блюд берутся по ID в порядке PostgreSQL.
- `Idempotency-Key` уникален в рамках клиента. Первое оформление возвращает 201, повтор с тем же содержимым — 200 и тот же заказ; изменённое содержимое даёт `409`.
- Статусы: `CREATED → PREPARING → DELIVERING → COMPLETED`. Только из `CREATED` можно перейти в `CANCELLED`; кухне обязательна причина. Отмена и смена статуса требуют текущий `expectedVersion`; при несовпадении — 409. Возврат остатка выполняется ровно один раз.
- Блокировка кухни отключает новые заказы, но сохраняет обработку существующих. Архивирование блюда не меняет снимки заказа.
- Отзывы разрешены только владельцу выполненного заказа и только один раз на его позицию. Скрытие требует причины; запись остаётся в БД и исключается из публичных агрегатов.
- Подбор использует веса 50/30/20 и только заполненные критерии. Округление — половина вверх; пустой профиль не имеет балла. Публичные отзывы не влияют на соответствие. Изменение предпочтений перепроверяет корзину в той же транзакции.

## Тесты и CI

Нужны JDK 21 и запущенный Docker:

```bash
cd backend
./mvnw -B verify
```

JUnit и Testcontainers поднимают **отдельную чистую PostgreSQL 17** на случайном порту, применяют реальные миграции и проверяют Hibernate-схему. `DB_PASSWORD`, `.env` и локальная БД проекта для тестов не нужны. Без Docker интеграционные тесты завершаются ошибкой, а не пропускаются молча. Контейнер удаляется после завершения.

Только формула и таблица переходов, без Docker:

```bash
./mvnw -B -Dtest=RecommendationScorerTest,OrderTransitionsTest test
```

Отчёты: `backend/target/surefire-reports/`. Workflow `.github/workflows/backend.yml` запускает `verify` для PR с изменениями backend и для `main`, сохраняет отчёты. Результаты запусков доступны в [GitHub Actions](https://github.com/RomoBomba/foodflow-delivery-service/actions/workflows/backend.yml).

Тесты проверяют миграции на чистой БД и обновление V11 → V12, роли и CSRF, конкурентные покупки и отмены, идемпотентность, откат транзакций, подтверждение цен, рекомендации и отзывы. Отдельная проверка запрещает доступ к репозиториям чужих модулей.

Браузерная приёмка выполняется вместе с frontend. Нагрузочные цели: p95 чтения ≤ 500 мс, оформления ≤ 800 мс, 5xx < 1%; функциональные тесты эти показатели не измеряют.

## Резервное копирование

При запущенном сервисе `postgres` (для локального режима задайте `COMPOSE_FILE=compose.yaml:compose.dev.yaml` в окружении терминала):

```bash
bash scripts/db-backup.sh
```

Копия сохраняется в `.local/backups/`; другой каталог можно задать через `BACKUP_DIR`. Это PostgreSQL custom dump без владельцев и привилегий.

Восстановление **заменяет содержимое текущей БД**; предварительно остановите backend и убедитесь, что выбрана нужная учебная база:

```bash
docker compose stop backend
bash scripts/db-restore.sh .local/backups/foodflow_YYYYMMDD_HHMMSS.dump
docker compose start backend
```

Восстановление идёт одной транзакцией и прерывается при ошибке. При восстановлении старой копии новые миграции применятся после запуска backend. Тома скрипты не удаляют.

## Работа команды

Изменения оформляются отдельными ветками и PR. Перед объединением нужны тесты и проверка соответствующих сценариев. `.env`, `.local/`, пароли, настройки IDE и результаты сборки не коммитятся. Временные тестовые данные не должны попадать в общую БД.
