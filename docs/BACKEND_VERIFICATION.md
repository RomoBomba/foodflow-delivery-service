# Проверка backend MVP

Дата: 6 ноября 2026 года. Основа изменений — PR №10, `danya-back`, commit `2d6245da2a1fbdf6373a44bf51b8258a8ea65956`. При начале работы PR был OPEN, mergeable, без запусков CI; удалённый `main` — `b0a759c`. Исправления и проверки подготовлены в интеграционной ветке `codex/foodflow-mvp` поверх исходных коммитов разработчика.

## Что исправлено

1. Корзина предварительно читает только `kitchenId`. Первое чтение сущности блюда происходит под блокировкой, после ожидания конкурентного изменения.
2. Отпечаток заказа кодирует длину каждого поля, сохраняя однозначность при переносах строк. Повторы заказов со старыми отпечатками поддерживаются только после сравнения сохранённых реквизитов и позиций.
3. После блокировки корзины ключ заказа проверяется всегда, включая случай повторного наполнения корзины.
4. Изменение предпочтений блокирует корзину до чтения и сохранения профиля; при отсутствии корзины создаётся строка для синхронизации с первым добавлением.
5. Формула рекомендаций использует точные количества совпавших и выбранных ингредиентов. Найденный случай: несовпавшая категория, 3 из 25 любимых ингредиентов, калорийность не задана — 4,5 округляется до 5, а не до 4.
6. Дробные JSON-значения целочисленных полей больше не усекаются: `quantity:1.5` отклоняется с 400. Необязательные флаги подтверждения можно опустить, значение по умолчанию false.
7. Повторные конкурентные отзывы и модерация сериализованы блокировкой соответствующего заказа/отзыва.
8. Проверка совместимости не раскрывает состав неопубликованных/архивных блюд; большая страница каталога не переполняет смещение JPA.
9. Ошибки JSON, типов и обязательных заголовков возвращают структурированный 400 без вывода исходного запроса. Фильтр идентификатора запроса запускается до Spring Security.
10. Добавлены контейнерный запуск backend, CI, демоданные и актуальные контракты frontend.

Миграции V1–V11 и версии runtime-зависимостей не менялись. Добавлены только тестовые зависимости под управлением существующего Spring Boot BOM. Маршруты и формы успешных HTTP-ответов сохранены.

## Автоматические проверки

Команда: `cd backend && ./mvnw -B verify`.

Результат: **74 теста, 0 ошибок, 0 неуспешных проверок, 0 пропусков**. Java 21, Spring Boot 4.1.2, PostgreSQL 17 через Testcontainers (фактически образ 17.11 при проверке). H2 не использовался. Проверки не подключались к локальной БД проекта.

| Группа | Покрытие |
| --- | --- |
| Миграции | Чистая PostgreSQL, применение V1–V11, `ddl-auto=validate`, начальные справочники |
| Корзина | Первая конкурентная запись, суммирование количества, предел 99, максимум 30 блюд, подтверждённая смена кухни, сохранение после нового входа |
| Актуальность блюд | Добавление и изменение количества после ожидания блокировки: архивирование, обнуление остатка, изменение цены — 6 случаев |
| Оформление | Последняя порция у двух клиентов, одинаковые параллельные запросы, разные реквизиты с тем же ключом, область ключа по клиенту |

| Транзакции | Ошибка PostgreSQL-триггера при записи истории после начала оформления; полный откат заказа, позиций, остатка и корзины; успешный повтор |

| Статусы | Все 25 пар переходов, обязательная причина отказа, гонка принятия с отменой, однократный возврат при двух отменах |
| Заблокированная кухня | Запрет новых покупок и выключение приёма, возможность закончить существующий заказ |
| Предпочтения | Конфликт любимых/исключённых ингредиентов, диапазон ккал, удаление несовместимых позиций, запрет добавления и оформления, синхронизация с изменением корзины |

| Отзывы | Только свой COMPLETED-заказ, без дубликатов, параллельная запись/модерация, обязательная причина скрытия, исключение из агрегатов |
| Агрегаты | Оценки 5/4/3 и ответы да/да/нет дают 4,0 и 67%; пустые значения без деления на ноль; пересчёт после скрытия |

| HTTP | Регистрация без возможности выбрать ADMIN, нормализация email, заявка/одобрение кухни, создание/редактирование/архивирование блюда, полный цикл заказа и отзыва |
| Границы API | Некорректный JSON, пропущенный ключ, неверный UUID, слишком большая страница, дробные количества, пустая выдача вне диапазона |

В конкурентных проверках каждая операция выполняется в своей транзакции и потоке. Для регрессий чтения блюда и повторного оформления тест удерживает блокировку и ждёт фактического блокирования второй транзакции через `pg_blocking_pids`, а затем завершает изменение. Проверки не опираются на фиксированную задержку для создания гонки.

### Подтверждение чувствительности регрессионных тестов

Три исходных дефекта были временно возвращены в локальные файлы. Выбранные 8 тестовых случаев завершились 7 assertion failures и одной ошибкой `CART_CHANGED` в ожидавшем повторе. После восстановления исправлений полный набор снова проходит. Это подтверждает, что тесты обнаруживают исходные ошибки, а не только выполняют текущие ветки кода.

Два дополнительных дефекта также сначала воспроизведены тестами: дробное количество получало 201 вместо 400; точный балл 4,5 округлялся до 4.

## Контейнерный запуск и сохранность данных

Создан отдельный Compose-проект `foodflow-mvp-check` на случайных loopback-портах и новом томе. Существующие контейнеры и тома проекта не использовались.

Проверено:

- Сборка backend Dockerfile и запуск вместе с PostgreSQL через профиль `app`.
- Запуск миграций на чистой БД и создание администратора из окружения с профилем `local`.
- `/api/health` возвращает 200.
- `scripts/demo.py --smoke` через настоящие cookie и CSRF создаёт 3 кухни и 20 блюд, оформляет заказ, безопасно повторяет оформление, проводит статусы до COMPLETED и публикует отзыв.
- `scripts/db-backup.sh` создаёт custom dump.
- Dump успешно восстановлен в отдельную пустую БД; совпали числа заказов, позиций и отзывов, сумма заказов и контрольная сумма ID/стоимости.
- `scripts/db-restore.sh` успешно восстановил исходную тестовую БД.
- Перезапуск PostgreSQL и backend сохранил контрольные значения.

Проверка восстановления использовала небольшой функциональный набор: 1 заказ, 1 позиция, 1 отзыв, сумма 175,00 руб. Она не измеряет время восстановления больших объёмов. Секреты и dump остаются вне Git.

## Что ещё требуется для приёмки всего приложения

- Frontend и совместный браузерный сценарий, адаптивность, доступность, опрос заказов и обработка сетевых ошибок реализует разработчик frontend. Эти проверки не заменяются MockMvc.
- Нагрузочные испытания NFR-01 на оговорённом стенде 2 vCPU / 4 ГБ с набором 10 кухонь, 1000 блюд, 1000 клиентов, 10 000 заказов; 20 пользователей, 1 минута прогрева и 5 минут измерений. p95 и доля 5xx здесь **не измерялись**.
- HTTPS-стенд, Secure-cookie и обратный прокси проверяются при развёртывании. Локальная проверка выполнена по HTTP.
- Истечение сессии через 30 минут задано конфигурацией, длительный тест ожидания не выполнялся.
- Результаты CI для опубликованных коммитов доступны в [workflow Backend](https://github.com/RomoBomba/foodflow-delivery-service/actions/workflows/backend.yml). Этот протокол фиксирует функциональное покрытие; статус конкретного коммита следует проверять по его запуску CI.

Наличие этих проверок и успешного функционального набора не является утверждением об отсутствии всех возможных дефектов или о готовности всего приложения вместе с frontend.
